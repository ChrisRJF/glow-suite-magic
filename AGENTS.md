# AGENTS

- AppLayout compactMobile is opt-in presentation spacing only; why: the mobile agenda can start higher without changing other pages or desktop layout.
- Agenda mobile and desktop date pickers reuse one local renderer with placement-specific open state; why: both date bars stay functional without mounting a second hidden calendar or changing shared calendar styles.
- Dashboard mobile finishing is scoped by data-mobile-dashboard and a mobile-only stylesheet block; why: shared layout and Autopilot components keep their desktop and other-page presentation unchanged.
- DashboardPage passes its existing tomorrow-risk count to TodayAtAGlance for mobile consolidation only; why: the customer-wide selector and both existing action destinations remain intact without changing desktop metrics.

- Per-tenant feature gates live in public.tenant_feature_flags (read-only for app users, set only by platform admins) and are enforced inside the SECURITY DEFINER RPCs; why: client flags or emails can be spoofed.
- Not-yet-approved edge code lives in supabase/functions/_shared/inactive/ and proposed SQL in docs/proposed-migrations/, never imported by an entrypoint; why: edge function edits deploy automatically.
- The customer email stop switch is the single row in public.customer_email_controls, read fresh on every send and fail-closed; why: a database value takes effect without redeploy, unlike secrets.
- Employee availability rules live only in supabase/functions/_shared/inactive/employeeSchedule.ts (re-exported by src/lib/employeeSchedule.ts) and are used by calendar, booking page and public-booking; why: one rule set prevents calendar and online booking from disagreeing.
- Onboarding quick start and extended setup share OnboardingWizard's saveSalon and finish paths; why: one completion path preserves preview isolation, default-service seeding and existing gate flags.
- Sidebar collapse preferences use the versioned v2 storage key and migrate legacy non-default groups; why: former default-open AI preferences must not override daily-first navigation while deliberate other choices survive.
- Agenda writes route per salon through agendaWriteCore's mode (flag true = atomic RPC only, false/missing = unchanged legacy until the slot guard, unreadable = no write); why: publishing must not block salons that are not switched on, and atomic salons must never fall back.
- Manual confirmation mails are sent only by the scheduled manual-confirmation-worker, scoped by server secrets (tenant + recipient allow-lists) and a per-tenant claim; temporary problems defer without using attempts and unclear provider outcomes are held, never marked sent; why: the outbox must never lose or falsely confirm a mail, and test scope must be enforced server-side.
- Appointment checkout counts money only from public.payment_ledger (service-role, written via record_provider_payment with provider-reported amounts), applies only to payments marked metadata.checkout = appointment_checkout, and is gated per salon by tenant_feature_flags.appointment_checkout_enabled; why: payments rows are client-writable and older payments must keep their existing flow.
- Kassa payments go through server orders (kassa_create_order prices from DB) and are settled only by kassa_settle_order after payment_ledger evidence; live requires kassa_live_allowed (platform flag + verified merchant); why: browser amounts, payments.status and salon-editable settings cannot be trusted.
- Kassa practice mode is gated by tenant_feature_flags.kassa_practice_enabled (platform-only) and confirmed only by kassa_practice_checkout; practice orders (is_practice) are refused by begin_attempt/attach/settle and never touch payments, ledger, stock or revenue; why: real salons must train without KYC or provider risk.
- Intake form e-mails go only through customer-forms + _shared/formRequestEmail.ts: hardcoded tenant allow-list FORM_EMAIL_TENANTS plus secret FORM_EMAIL_RECIPIENTS (unset = deny), the customer_email_controls stop switch, and resend token rotation committed only after provider acceptance; why: tests must never reach real customers and a failed send must not invalidate a working link.
- Subdirectories have their own AGENTS.md (e.g. supabase/functions/); read it before changing files there.
- Platform-wide owner data (/platform) is read only through SECURITY DEFINER RPCs that call platform_require_owner_aal2 and write audit_logs; the sidebar link and page gate are UI hints only; why: salon users must never read cross-tenant data or ISV commissions.
- MFA settings only ever unenroll unverified setups or an explicitly chosen verified factor, and hide removal of a platform owner's final factor (docs/security/platform-owner-mfa.md); why: Supabase Auth cannot block final-factor unenroll server-side, so the UI is a hint and recovery is an admin procedure.
- Reminders use _shared/reminderSafety.ts for tenant-scoped loads before claims and exact start instants; why: DST and mixed storage must not mis-send.
